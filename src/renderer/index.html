Vault & password

Your master password encrypts every private key at rest. Changing it re-seals the vault; the old password stops working immediately, including for backups taken after the change.

Backup & restore

Saves your keys (still encrypted), categories, saved servers, known hosts, settings, MCP servers and SFTP bookmarks as one sealed file, written by SSHSpan itself - the vault never passes through this window. Not included: Bitwarden sync settings and AI-assistant settings, so set those up again after restoring on another machine. Restored MCP servers stay switched off until you confirm them. Restoring needs the master password that was current when the backup was taken.

Backups are sealed with your master password - treat the file as a secret.

Bitwarden / Vaultwarden sync

Keeps your SSH keys and saved servers mirrored as items in your own vault (folders SSHSpan_Keys and SSHSpan_Servers by default). Two-way: changes sync in both directions, newest wins; changes coming from Bitwarden that would replace or add data here wait for your approval, and deletions are never propagated automatically. Self-hosted servers must use a public hostname - private, LAN and localhost addresses are refused for safety. The stored vault password is sealed with your SSHSpan master password and only readable while the vault is unlocked.

    AI assistant

    An optional chat assistant docked beside the terminal (Ctrl+Shift+A). It can read the live terminal and help with server administration; what it may do is a per-tab access level chosen on the panel (Read / Draft / Execute / YOLO). The API key is sealed with your vault master password, all provider traffic goes through the app backend, and every AI-executed command is written to the audit log. Off by default.

    Works with OpenAI, OpenRouter, Groq, Anthropic, and local servers like Ollama / LM Studio.

    MCP servers

    Optional Model Context Protocol servers - external tool providers (search, databases, SaaS APIs) the assistant can call when you enable their tools. Tools stay off until you approve them here, are re-checked when their definition changes, and every call still goes through the panel's access level and per-call approval (except in YOLO or when you tick Auto-approve for a tool).

    Add MCP server

    Plain HTTP on a loopback address - traffic to this server is not encrypted or authenticated. Fine for a local proxy, not for anything remote.

    MCP tools are offered to the assistant only when enabled below, stay behind the access level, and (outside YOLO) behind per-call approval.

    Enable YOLO mode?

    At YOLO the assistant runs commands without asking you each time. It has full autonomous control of the live SSH session: it can read and change anything the account you connected with can reach, and it is logged in as that user.

    Every command is written to the audit log, but nothing is confirmed with you first. Only enable this if you trust the current session, the provider, and the model - or nothing on the server can hurt you.

    Anything printed in this terminal (logs, files, command output) can influence what the AI decides to run. Only enable YOLO on sessions where you trust everything that appears on screen.

    With MCP servers connected, injected terminal text can make the AI act on those services with your credentials. YOLO used to reach one host; with MCP it reaches every connected account.
