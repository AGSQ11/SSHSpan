## A3-01: DnD wiring and Preserve-timestamps toolbar button are dead - they run while the panel is still detached from the document
- **Severity:** Medium
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:559-561` (calls), `:570-573` (`ensureSftpPreserveTsToggle` early return), `:3521-3525` / `:3551-3552` (`wireSftpPaneDnd`), `:3616` (document drop handler relies on the dead wiring), `:192-196` (`showSftpForTab` appends the panel only after `buildSftpPanel` returns)
- **Evidence:** `buildSftpPanel()` ends with `wireSftpPaneDnd(tabId); ensureSftpPreserveTsToggle(tabId); return panel;` but the panel is appended to `#sftpBody` by the caller afterwards (`panel = buildSftpPanel(tabId); sbody.appendChild(panel);`). Both helpers locate their targets with `document.getElementById(...)`, which returns `null` for a detached subtree: `wireSftpPaneDnd` finds neither `sftpLocalTbody-<id>` nor `sftpTbody-<id>` (no listener is ever attached), and `ensureSftpPreserveTsToggle` hits `if (!panel || ...) return;` so `#sftpPreserveTsBtn-<id>` is never created. Neither helper is called from anywhere else (grep). There is no Settings toggle for `sftpPreserveTs` either (no match in app.js/index.html).
- **Why it is a flaw:** (1) In-app drag and drop onto a folder row (remote->local "download into folder", local->remote "upload into folder", remote->remote move) does nothing: the document-level fallback at `:3616` deliberately returns for directory rows because it assumes "those were consumed by the tbody delegation". (2) The "Preserve timestamps of transferred files" feature has no reachable control, so it is permanently off for anyone who never had the DB key set.
- **Proposed fix:** call `wireSftpPaneDnd(tabId)` and `ensureSftpPreserveTsToggle(tabId)` from `showSftpForTab` right after `sbody.appendChild(panel)` (both are idempotent), or make them take the element references instead of looking them up through `document`.
- **Confidence:** confirmed (code reading; reproduction results recorded below if run)
- **Effort:** S


## A3-02: Transfer panel and `sftp_queue_list` re-trigger each other forever whenever the queue is empty
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:3399` (end of `renderQueuePanel`: `if (!queueJobs.size) call('sftp_queue_list')`), `:2938-2949` (`wireQueueEvents` listener calls `renderQueuePanel()` for every `sftp-queue` event), `:3032-3036` (tab buttons), `:3055-3061` (Clear finished); Rust `src-tauri/src/sftp/queue.rs:536-541` (`emit_queue` always emits the full snapshot, also `{jobs: []}`), `src-tauri/src/commands/sftp.rs:1293-1298` (`sftp_queue_list` is a synchronous command, i.e. it runs on the main thread)
- **Evidence:** `renderQueuePanel` asks the backend for "authoritative state" whenever `queueJobs` is empty. The backend answers by emitting `sftp-queue` with the whole (empty) snapshot, the listener runs `renderQueuePanel()` again, `queueJobs` is still empty, so it asks again. Reproduced in headless Chromium against the real renderer with a stub that behaves like `emit_queue`: clicking the "Done" tab with no transfers produced 210 `sftp_queue_list` calls in the first second and 411 after two seconds; it only stopped once a job existed. "Clear finished" empties `queueJobs` (`:3057-3059`) and starts the same loop; the Queued/Failed/Done buttons are always on screen.
- **Why it is a flaw:** an unbounded IPC + event + full DOM rebuild (`list.innerHTML = ''`, grouping, icons) loop that starts from one ordinary click and keeps a core busy on both the webview and the Rust main thread (sync command) until the next transfer is queued. Fans spin, battery drains, and the UI thread is shared with every other IPC call.
- **Proposed fix:** drop the re-entrant call from `renderQueuePanel`; request the snapshot exactly once from `wireQueueEvents()` right after the listener is registered (and when the queue panel is first built). If it must stay, guard it with a `queueSyncRequested` flag that is cleared only by a non-empty snapshot or a timer.
- **Confidence:** confirmed (reproduced with a faithful IPC stub; Rust side confirmed by reading)
- **Effort:** S

## A3-03: Pause/Cancel on a running transfer usually does nothing - the queue list is rebuilt on every progress event
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:3394` (`list.innerHTML = ''` in `renderQueuePanel`), `:2938-2949` (every `sftp-queue` event re-renders), `:3302-3347` (listeners are attached to per-render buttons); Rust `src-tauri/src/sftp/queue.rs:959-967` and `:1016` (one delta event per active job at least every 200 ms)
- **Evidence:** a click needs mousedown and mouseup on the same DOM node. Each progress event destroys and recreates every row and button, so a press that spans a re-render is dropped. Measured in headless Chromium on a 1600x1000 viewport with one active job emitting an update every 200 ms and a stationary pointer on the Cancel button (20 attempts per row): control without events 5/5 delivered; 60 ms press 15/20 delivered; 120 ms press (a normal click) 4/20 delivered. With the default `sftpParallel=2` the event rate doubles.
- **Why it is a flaw:** the only way to stop or pause a running transfer is unreliable exactly while it is running; users click repeatedly and the Pause/Cancel/Retry affordances look broken. Hover and tooltip state also reset 5 times a second.
- **Proposed fix:** stop rebuilding the list per event. Keep a `Map<jobId, rowEl>` and patch the progress bar, speed/ETA text and the button set in place (replace a row's buttons only when its `state` changes). Delegating the click handler is not enough by itself because the mousedown target would still be detached; if a full rebuild is kept, coalesce renders with `requestAnimationFrame` and skip them while a pointer is pressed inside `#sftpQueueList`.
- **Confidence:** confirmed (reproduced with measured delivery rates)
- **Effort:** M

## A3-04: A failed directory open leaves `tab.sftpPath` on the unreadable folder while the UI still shows (and acts on) the old listing
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:1397-1398` and `:1406-1408` (`sftpActivateEntry`: `tab.sftpPath = full; refreshSftpPanel(tabId)`), `:1513-1514` (`sftpNavigateUp`), `:1946-1948` (search result click), `:1996-1998` (bookmark click), `:3902-3910` and `:3928-3929` (synchronized browsing); `refreshSftpPanel` `:905-939` only toasts in its `catch` (`:936-938`), whereas `sftpUiNavigateRemote` does revert (`:719-721`)
- **Evidence:** every caller assigns the new path first and lists afterwards; the listing error path never restores it and never redraws the crumbs. Reproduced (A3 scratch probe p1): list `/home/u` = `secret/`, `notes.txt`; make `sftp_list_dir('/home/u/secret')` reject with "Permission denied"; double-click `secret` -> toast, but `tab.sftpPath === "/home/u/secret"` while rows and breadcrumb still show `/home/u`. Choosing Download on the visible `notes.txt` then queued `{remote: "/home/u/secret/notes.txt"}`.
- **Why it is a flaw:** unreadable folders (`/root`, `lost+found`, other users' homes) are routine on servers. After one, every operation built from `tab.sftpPath` - Download/upload target, New folder/file, Rename, Delete, chmod, bookmark, Copy path/URL, "Send to" - targets a directory the user is not looking at, with names taken from another one.
- **Proposed fix:** make navigation transactional: one helper `sftpNavigate(tabId, path)` that remembers `prev`, lists, and only then assigns `tab.sftpPath`; if the listing throws, keep `prev` and re-render nothing. `refreshSftpPanel(tabId, {path})` can take the target as an option instead of reading it from the tab.
- **Confidence:** confirmed (reproduced)
- **Effort:** M

## A3-05: Selection is a set of names that survives dotfile toggle, quick-find and directory changes, so Delete/Download/chmod act on rows the user cannot see
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:1221` (`renderEntries` prunes against the FULL `_entryMap`, not the visible list), `:924-926` and `:711-715` (navigation/refresh never clear `sftpSelected`), `:1666-1684` and `:1710-1741` (menu builds `selected`/`selectedPaths` from the whole set), `:1695` (chmod), `:1683` (download), `:1714-1718` (confirm text only gives a count)
- **Evidence:** reproduced (A3 scratch probes p6 and `selection_carry`): (1) show dotfiles, Ctrl+A (4 rows: `.ssh .bashrc a.txt b.txt`), switch Hidden off: visible rows `a.txt b.txt`, status bar "2 items - 4 selected", `sftpSelected` still has the dotfiles; right-click `a.txt` -> "Delete 4 items"; confirming sends `sftp_remove` for `/home/u/.ssh`, `/home/u/.bashrc`, `/home/u/a.txt`, `/home/u/b.txt`. (2) Select `index.html` in `/a`, navigate to `/b` (which also has `index.html`): the row in `/b` is highlighted and selected. (3) Type-to-filter hides selected rows the same way.
- **Why it is a flaw:** the selection is keyed by bare file name and is only pruned when the name no longer exists in the new listing. Destructive actions therefore reach hidden dotfiles (e.g. `.ssh`, `.env`) and same-named files in other directories, and the confirmation ("delete these 4 items") does not name them.
- **Proposed fix:** clear `tab.sftpSelected` whenever `tab.sftpPath` changes, and in `renderEntries` intersect the selection with the currently visible names (`visible`) so hidden or filtered rows are deselected; list the first few names in the delete confirmation.
- **Confidence:** confirmed (reproduced)
- **Effort:** S

## A3-06: Conflict "Rename" picks `name (1).ext` without checking it is free and then overwrites the file that already has that name
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:2838-2854` (`applyConflictAction`: `taken` is only `{destEntry.name}`; `extraTaken` is never passed by its callers at `:2655` and `:2789`), `:2624-2631` (`sftpFreeName`), `:2573` (upload sends `remote: d.renameRemote, resume: 'rename'`), `:2512-2513` (download sends `localName`); misleading comment `:2832-2837`; Rust `src-tauri/src/sftp/queue.rs:99-106` (`from_str_loose("rename")` falls through to `Overwrite`) and `:1448-1456`/`:1653-1657` (finalize removes an existing destination and renames over it)
- **Evidence:** the doc comment says Rename "computes the free name against the destination listing (plus names already claimed by this batch)", but only the conflicting entry's own name is considered. Reproduced (A3 scratch probe p3): `/srv` contains `a.txt` and `a (1).txt`, conflict mode = Rename, upload `/tmp/a.txt` -> `sftp_queue_add` item `{remote: "/srv/a (1).txt", resume: "rename"}`. The worker then replaces the existing `a (1).txt`. Two same-named sources in one batch collapse onto the same `name (1)` for the same reason.
- **Why it is a flaw:** "keep both" is exactly what users pick to avoid data loss; the second time they do it for the same file the earlier copy is silently destroyed (upload and download).
- **Proposed fix:** in `queueUploads`/`queueDownloads` build `taken` from the destination listing already fetched there (`remoteEntries.get(dir)` / `localEntries`) plus names assigned earlier in the batch, and pass it as `extraTaken`; keep incrementing in `sftpFreeName` until the name is absent from that set.
- **Confidence:** confirmed (reproduced; backend overwrite confirmed by reading)
- **Effort:** S

## A3-07: Every completed transfer re-renders the file table and moves keyboard focus into it - out of the terminal (split mode), the path editor and the Rename/New-folder prompts
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:3403-3411` (1.5 s ticker: any job reaching `done` refreshes the active tab), `:905-939` -> `:1230` -> `:1002-1012` (`sftpRestoreRowFocus` calls `row.focus()` for `tab._focusedName` unconditionally), `:1363-1371` (printable keys on a row become quick-find with `preventDefault`), `:1330-1334` (Enter activates the row)
- **Evidence:** `_focusedName` is set by any earlier click/focus on a row and never cleared. Reproduced in headless Chromium: (1) split mode, terminal focused (`xterm-helper-textarea`), a transfer finishes -> after ~2 s the active element is the `tr` of the previously clicked file; typing `ls` sends nothing to the shell and starts a quick-find (list collapses to nothing). (2) typing `/var/w` in the path editor, a transfer finishes -> focus is on a row, the editor is hidden by its `blur` handler, further keys go to quick-find. (3) while the Rename prompt is open and being typed into, a transfer finishes -> focus drops out of the input (`BODY`), later keystrokes are lost.
- **Why it is a flaw:** completing a background transfer (the normal case for the queue) silently hijacks whatever the user is typing; with a match, Enter then downloads or opens the focused file instead of running the shell command. `refreshSftpPanel` already avoids overwriting the path box value while it has focus (`:928`), but the focus steal defeats that care.
- **Proposed fix:** restore row focus only when focus was inside the table before the rebuild (`const had = tbody.contains(document.activeElement)` captured at the top of `renderEntries`) and no modal/input is focused; background refreshes should call `renderEntries` with `{restoreFocus: false}`.
- **Confidence:** confirmed (reproduced)
- **Effort:** S

## A3-08: Keystrokes typed into the terminal never reset the vault idle timer, so auto-lock fires mid-typing and kills every live session
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/app.js:4536-4540` (bubble-phase passive `keydown`/`mousedown`/`wheel`/`touchstart` listeners on `document` call `resetAutoLockTimer`), `src/renderer/terminal.js:298-350` (xterm instance whose key handler cancels and stops propagation of every key it handles); `src-tauri/src/commands/mod.rs:378-404` (`lock_vault_internal`: `kill_all()` sessions, `SftpRegistry::clear`, `queue::pause_all`)
- **Evidence:** xterm calls `preventDefault()`+`stopPropagation()` on the keys it turns into terminal data, so those events never bubble to `document`. Reproduced in headless Chromium with `autoLockMinutes=15`: typing `vim /etc/nginx/nginx.conf`, Enter, ArrowUp/Down, Tab, Backspace, Escape, Ctrl+C, Ctrl+R into the focused xterm produced only 3 `keydown`s at `document` (one space and two bare `Control` presses); the reset counter rose by 2 for 15 typed characters, while one mouse click rose by 1 (A3 scratch `probe-term t7`, `probe-keys2`).
- **Why it is a flaw:** anyone who works in a shell/editor for `autoLockMinutes` without clicking or scrolling (editing a file in vim, watching logs) is "idle" to the timer. The lock then terminates all SSH sessions and pauses transfers while the user is actively working - lost sessions, unsaved editor state on the remote, interrupted jobs.
- **Proposed fix:** register the activity listeners in the capture phase (`document.addEventListener(ev, handler, { capture: true, passive: true })`) so xterm's `stopPropagation` cannot hide them, and additionally call `resetAutoLockTimer()` from the terminal's `onData` handler (`terminal.js:541`).
- **Confidence:** confirmed (reproduced)
- **Effort:** S

## A3-09: Directory listings are not sequenced - a slow older listing overwrites the newer navigation (path, rows and breadcrumb)
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:905-939` (`refreshSftpPanel`: `const path = tab.sftpPath` at :911, `await sftpCall('sftp_list_dir')` at :919, then unconditional `tab.sftpPath = canonicalPath` / `sftpSetEntries` / `renderEntries` at :924-930), `:682-723` (`sftpUiNavigateRemote`: same shape, :697 / :706 / :711); triggers `:1397-1408` (double-click), `:1513-1514` (Up), `:3403-3411` (1.5 s transfer-done refresh)
- **Evidence:** there is no request token or "latest wins" check. Reproduced (A3 scratch `q1-sftp-logic.js`, `race`): `sftp_list_dir('/home/u/slow')` takes 400 ms, `/home/u/fast` takes 30 ms. Double-click `slow`, 100 ms later navigate to `/home/u/fast`: at +150 ms the UI correctly shows `/home/u/fast`; at +650 ms the late `slow` reply lands and the tab ends with `tab.sftpPath === "/home/u/slow"`, rows `file-in-slow.txt` and breadcrumb `/>home>u>slow` - the older navigation wins. The Rust command returns the path exactly as sent (`commands/sftp.rs:287`), so the stale reply carries no hint it is stale.
- **Why it is a flaw:** on a slow link or a big directory (seconds) any two quick navigations (double-click then crumb/Up, or the background refresh that fires when a transfer completes while the user is already moving) leave the user looking at a directory they did not ask for. Because every operation (download, rename, delete, chmod, upload target, New folder) is built from `tab.sftpPath`, the next action then lands in the wrong directory.
- **Proposed fix:** give each tab a monotonically increasing `tab._listSeq`; capture `const seq = ++tab._listSeq` before the await in both functions and `return` after the await if `seq !== tab._listSeq`. Combine with the transactional-navigation change proposed in A3-04 (assign `tab.sftpPath` only once the winning reply is applied).
- **Confidence:** confirmed (reproduced)
- **Effort:** S

## A3-10: The header "Reconnect" button connects whichever server is selected in the list - in a NEW tab - instead of reconnecting the dead tab
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/app.js:3466-3469` (click handler: `const srv = currentSelectedServer(); if (srv) openSessionTab(srv);`), `:3677-3679` (`currentSelectedServer` = `state.connectSelectedId`), `:3765-3776` (row clicks call `selectServer`), `:4380` (`termReconnectBtn.hidden = live` - the button is offered for the ACTIVE tab), `:4272-4292` (`activateSessionSurface` never updates `connectSelectedId`); the correct same-tab path `reconnectActiveTab` (`:4243-4269`) is only reachable from the terminal context menu (`:1293`)
- **Evidence:** reproduced (A3 scratch `q3-terminal.js`, `headerReconnect`): tabs `PROD` (ended) and the list selection on `STAGING`; activating the PROD tab shows the Reconnect button; clicking it issues `terminal_connect {serverId: "staging"}` and the tab list becomes `PROD(ended)`, `STAGING`. The dead PROD tab is untouched.
- **Why it is a flaw:** the button sits in the header of the PROD tab, is labelled for that tab, and opens a shell on a different host (the last row the user happened to click). In an SSH client that is a wrong-environment connection - the user types commands meant for prod into staging (or the reverse) and still has a dead tab. Even when the selection happens to match, the old tab keeps its dead state and a duplicate tab appears.
- **Proposed fix:** make the header button call `reconnectActiveTab()` (it already resolves the server from `tab.serverId`) whenever there is an active tab, and use `openSessionTab(currentSelectedServer())` only in the no-tab case that `updateTerminalHead` already distinguishes (`:4382-4388`).
- **Confidence:** confirmed (reproduced)
- **Effort:** S

## A3-11: Context-menu / right-click / Ctrl+Shift+V paste bypasses xterm's paste(): no bracketed-paste markers and raw LF instead of CR
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/terminal.js:656-671` (`window.terminalPaste` ends in `return sendTerminalBytes(rec, text)` at :670), `:146-153` (`sendTerminalBytes` -> `terminal_send` with the raw text), callers `:252-261` (right-click on the helper textarea), `:262-274` (Ctrl+Shift+V), `src/renderer/app.js:1286` (menu "Paste"); the fallback `t.paste(...)` at `:259`/`:271` is only used when `window.terminalPaste` is missing
- **Evidence:** the earlier fix (comment at :245-251) replaced `t.paste()` with `terminalPaste` to get the confirmation dialog and focus restore, but `terminalPaste` writes the clipboard text straight to the channel. Reproduced (A3 scratch `q3-terminal.js`, `paste`): after the remote enabled DECSET 2004 (`term.modes.bracketedPasteMode === true`), `terminalPaste('t1', 'echo one\necho two')` sent the bytes `echo one\necho two`; xterm's own `term.paste()` of the same text emits `ESC[200~echo one\recho two ESC[201~`. Plain Ctrl+V and Linux middle-click still go through xterm's native path, so the same clipboard behaves differently per gesture.
- **Why it is a flaw:** bracketed paste is what makes bash >= 5.1/zsh/vim/nano treat a paste as data. Without it a multi-line paste executes line by line as it arrives (the "review before running" safeguard the setting promises is gone - and its `confirm()` is already a no-op, see the earlier findings), vim with autoindent produces staircase text, and in nano each LF (Ctrl+J) triggers Justify. LF instead of CR also differs from what a real Enter sends.
- **Proposed fix:** after the confirmation, call `rec.term.paste(text)` (it wraps in 200~/201~ when the app asked for it, normalises `\r?\n` to `\r`, and emits through `onData`, i.e. the existing `terminal_send` subscription) instead of `sendTerminalBytes`; keep `sendTerminalBytes` for `terminalSendText` (assistant "Insert").
- **Confidence:** confirmed (reproduced)
- **Effort:** S

## A3-12: With more than 100 pending transfers the Queued tab drops the RUNNING jobs (and the next-to-run ones) from the list - their progress, Pause and Cancel disappear
- **Severity:** High
- **Category:** js-logic
- **Location:** `src/renderer/sftp.js:3390-3397` (`shown = [...active, ...queued, ...paused]` then `sftpQueueRenderGroups(list, shown.slice(-100))`), summary computed from the full arrays at `:3364-3377`; row buttons `:3302-3347`
- **Evidence:** `slice(-100)` keeps the LAST 100 entries, but `active` jobs are first in the array. Reproduced (A3 scratch `q1-sftp-logic.js`, `queue`): emit `sftp-queue` with 2 active + 150 queued jobs. Header summary: "2 active - 2.0 KB/s - 150 queued"; list rows: 100, from `queued-050.bin` to `queued-149.bin`; neither active job is rendered, and queued 000-049 (the ones that run next) are hidden too. A folder upload/download is expanded server-side into one job per file (`commands/sftp.rs:1285-1289`, `expand_download`/`expand_upload`), so >100 jobs is the normal case for any directory transfer.
- **Why it is a flaw:** the user sees "2 active" but cannot find them, cannot pause or cancel the transfer that is consuming bandwidth (only the global Pause all remains), and the visible rows are the ones furthest from running. The truncation is silent - no "+N more" row.
- **Proposed fix:** never truncate the running/paused set: `const head = [...active, ...paused]; const tail = queued.slice(0, Math.max(0, 100 - head.length))` for the Queued tab (oldest = next to run first), keep `slice(-100)` for Done/Failed, and append a "... and N more" row when anything was cut.
- **Confidence:** confirmed (reproduced)
- **Effort:** S

## A3-14: Two overlapping connects on one tab (Restart while a connect is pending): the first session leaks and the second loses its close detection

## A3-32: Terminal output is decoded per SSH packet with `from_utf8_lossy`, so a multi-byte character split across two packets becomes U+FFFD garbage
- **Severity:** Medium
- **Category:** rust-logic
- **Location:** `src-tauri/src/ssh_client/mod.rs:693-710` (`ChannelMsg::Data` and `ExtendedData`: `String::from_utf8_lossy(&data)` then `on_data.send(text.to_string())`, no carry buffer), `src-tauri/src/commands/terminal.rs:141` (`on_data: Channel<String>`), renderer side `src/renderer/terminal.js:514-522` (`t.write(text)` receives already-damaged text)
