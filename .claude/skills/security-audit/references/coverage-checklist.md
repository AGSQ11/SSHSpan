# Coverage checklist

The other references are depth. This one is breadth: a tick-list to answer
"did I skip an area?" before calling an audit complete. Most entries will be
"checked, nothing found" — record that, because an audit with no coverage
statement is indistinguishable from an audit that did not look.

Organised against Tauri's application-lifecycle phases and the OWASP Thick
Client ASVS chapters, plus the areas that fall between both.

## Lifecycle phases

### Upstream
- [ ] `cargo audit` clean; RustSec advisories triaged
- [ ] Tauri and plugin versions current; check advisories for the pinned major
- [ ] npm devDependencies (`@tauri-apps/cli`, `api`) current
- [ ] Duplicate or unmaintained crates, especially crypto and parsing
- [ ] Vendored/bundled third-party code reviewed

### Development
- [ ] No secrets in the repo: keys, tokens, passwords, `.env`, keystores
- [ ] No secrets in **git history** (`git log -p -S` for likely markers) — a
      rotated key still in history is still leaked
- [ ] Test fixtures contain no real credentials or real private keys
- [ ] Dev servers and debug endpoints cannot be reached in a release build
- [ ] `examples/` and test binaries cannot ship; they bind to loopback
- [ ] Debug-only escape hatches (env-var overrides, bypass flags) are
      `#[cfg(debug_assertions)]`

### Build time
- [ ] CI actions pinned to commit SHAs
- [ ] Signing keys handled without leaking into logs; removed on exit
- [ ] Build steps that post-process artifacts run *before* signing
- [ ] Artifact globs match reality and fail loudly when they match nothing
- [ ] `build.rs` and any codegen reviewed — it runs on every developer machine
- [ ] Generated committed files regenerated by tooling, diffed on review

### Distribution
- [ ] Release artifacts signed; signatures published alongside
- [ ] Update metadata and binaries cannot be swapped independently
- [ ] Checksums are not the only integrity control
- [ ] Platform packaging correct (see `tauri-desktop.md` on AppImage)
- [ ] Download page / release notes do not instruct users to bypass warnings

### Runtime
- [ ] Covered by the other reference files

## TCASVS chapter mapping

### V1 Architecture and threat modelling
- [ ] Trust boundaries enumerated and current (SKILL.md has the map)
- [ ] Every IPC command attributed to a boundary
- [ ] Security-relevant docs (SECURITY.md, PRIVACY.md, README claims) match the
      code — stale claims are findings

### V2 Build, deployment, environment hardening
- [ ] Release binary hardening: PIE/ASLR, stack protector, RELRO, NX. On
      Windows check `/DYNAMICBASE`, `/NXCOMPAT`, CFG. Report absence as low,
      since these are cheap and bound exploitability of any memory bug in C
      dependencies
- [ ] Code signing: Windows Authenticode, macOS signing and notarisation if
      those targets ship. An unsigned binary trains users past OS warnings
- [ ] Debug symbols and `devtools` off in release
- [ ] Panic behaviour: does a panic produce a core dump containing secrets?
- [ ] Installer/uninstaller: does uninstall leave the vault, keys, or temp
      files behind, and is that documented?

### V3 Data storage and protection
- [ ] Everything in `crypto-secrets.md` under "on disk"
- [ ] Application data directory permissions
- [ ] Crash/telemetry files, if any
- [ ] Clipboard lifetime for copied secrets
- [ ] Screenshot/screen-capture exposure of secrets (informational — some OSes
      offer window-level protection)

### V4 Code quality and exploit mitigation
- [ ] `rust-backend.md` classes swept
- [ ] `unsafe` blocks: count them, and each one's invariant documented
- [ ] FFI boundaries, if any
- [ ] `cargo clippy` clean on security-relevant lints

### V5 Cryptography
- [ ] `crypto-secrets.md` swept end to end

### V6 Network communication
- [ ] Every outbound destination enumerated — updater, Bitwarden, anything else
- [ ] TLS verification never relaxed anywhere, including test paths
- [ ] Redirects re-validated for host and scheme
- [ ] Response size and time bounds
- [ ] Proxy handling does not leak credentials
- [ ] DNS rebinding considered where a hostname is resolved twice (check then
      connect) — resolve once and connect to the resolved address
- [ ] No plaintext HTTP for anything security-relevant

## Easy to forget

These are the ones that get skipped. Check them explicitly.

- [ ] **Denial of service** — unbounded allocation from server-supplied sizes,
      pathological directory listings, KDF cost parameters, regex on untrusted
      input, decompression ratios. DoS on a desktop app is lower severity than
      on a server, but a hang during a security dialog changes user behaviour
- [ ] **Audit log integrity** — is there one, does it record security events
      (host-key decisions, exports, deploys, restores), can the renderer forge
      or suppress entries, and does it leak secrets?
- [ ] **Privacy / telemetry** — what leaves the machine and when. An update
      check on by default is a network callback; is that disclosed?
- [ ] **Error messages** — do they leak paths, usernames, key material or
      internal state to the UI, to logs, or to a remote?
- [ ] **Time and clock** — expiry checks that a user can defeat by changing the
      clock; certificate or token validity
- [ ] **Unicode handling** — normalisation differences that defeat an
      allowlist, RTL override in displayed names, homoglyph confusion in host
      names and key names
- [ ] **Deep links, URL schemes, file associations** — any registered handler
      is an unauthenticated entry point from another local app or a browser
- [ ] **Drag and drop into the window** — a path or payload from outside
- [ ] **Single-instance handling** — the second-launch callback receives argv
      from another process; treat it as input
- [ ] **Other local processes** — anything listening on a socket or named pipe,
      and whether it authenticates its peer
- [ ] **Idle lock and session teardown** — does locking actually clear derived
      keys and kill live sessions, or only change the UI?
- [ ] **Backup and restore round-trip** — covered in `ssh-sftp.md` for planted
      trust, but also check what a restore can overwrite
- [ ] **Uninstall and key deletion** — residue on disk
- [ ] **Accessibility of security UI** — a consent dialog that cannot be
      operated by keyboard, or whose destructive action is the default focus,
      produces wrong decisions. This is a security finding, not a UX nit
- [ ] **Dead surface** — unused plugins, unregistered commands, unreachable
      permissions. Each one is something a future change can accidentally
      re-expose

## Closing the audit

Before reporting, confirm you can answer:

- Which boundaries did I sweep, and which did I not?
- For each reference file, did I actually apply it or just skim it?
- What could I not verify in this environment, and did I say so?
- For every "clean" area, what did I actually check to conclude that?
