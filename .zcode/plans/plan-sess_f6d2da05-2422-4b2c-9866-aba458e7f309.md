# Embedded SSH Client ("Connect") — Tauri v2, Windows + Linux

## Honest framing up front

"Replicate PuTTY 100%" is not literally reachable in an app whose renderer is an HTML webview (xterm.js is an excellent terminal emulator, but cursor/select/paste semantics differ from the native Win32 console, and PuTTY's session tree is a registry file). What I will build is a **PuTTY-grade interactive SSH terminal**: full-screen-ish VT/ANSI session in its own tab, saved servers with name/host/port, per-server **user + SSH key binding**, key fingerprint display, host-key verification with fingerprint trust-on-first-use, configurable connection settings, and right-click-on-a-key → "Use this to connect…". Auth methods: publickey (in-vault key or .pem file), password, and keyboard-interactive.

Three things are worth stating plainly so the scope is honest:
- **Terminal emulation = xterm.js** (the same engine VS Code uses), vendored into `src/renderer/vendor/` and loaded as plain `<script>`/`<link>` — this keeps the strict `script-src 'self'` CSP intact with no bundler, no CDN, no `node_modules` at runtime.
- **SSH client = russh** (Tokio, Apache-2.0, actively maintained; used by warp-gate and a number of terminal apps). It supports in-memory keys, publickey/password/keyboard-interactive auth, PTY requests + window resizing, and OpenSSH certificates. No local ConPTY/pty is needed — russh sends the `pty-req` itself and streams raw channel bytes; the only PTY is the remote one on sshd. (Windows-native console behavior like PuTTY's local echo of typed lines doesn't apply — we're a proper terminal, so the remote shell handles echo, which is what a "real" terminal does.)
- **Session store = our SQLite DB** (`servers` table), not a PuTTY registry file, and not `~/.ssh/config` (that file stays owned by the existing Deploy feature).

## Design decisions (defaults chosen since no answers came back — all easily flippable)

1. **Vault-gated.** The Connect feature requires an unlocked vault, matching the existing Deploy flow. When the vault locks, all live SSH sessions disconnect and Connect is disabled until re-unlock. Keys never leave the vault.
2. **Sessions store a key *reference*, never key material.** `servers.key_id` points at `keys.id`. At connect time Rust unseals that key in-process (`VaultPasswordStore` already holds the master password — the renderer never sees the private key bytes) and feeds them to russh. A stored `.pem` path is supported as an alternative; deleting a key later shows a warning on saved sessions that used it.
3. **Interactive remote shell.** After auth, request a PTY and let the user's default remote shell run; terminal resize sends `window-change`. (`saved-sessions.md` from the roadmap-style future — no shell selection needed in v1.)

## New files

**Rust**
- `src-tauri/src/ssh_client/mod.rs` — russh glue: `client::Config`, key loading from decrypted in-memory PEM bytes (russh `keys::decode_secret_key`), auth selection (publickey → password → keyboard-interactive fallback), PTY request, resize, and the `Handler` that:
  - `check_server_key` → host-key TOFU against our `known_hosts` table (fingerprint compare); on first sight stores host + key + fingerprint, on mismatch disconnects with a clear error.
  - `channel_open_session`, `auth_banner`, data/exit/close plumbing to the byte channel.
- `src-tauri/src/ssh_client/pty.rs` (optional small split) — remote PTY term + window-change helpers.
- `src/renderer/vendor/xterm.js`, `xterm.css`, `addon-fit.js`, `addon-web-links.js` — copied from `node_modules/@xterm/*` (they ship UMD builds), committed to the repo so builds never need npm.

**Renderer**
- `src/renderer/terminal.js` — thin wrapper around the vendored xterm.js: create `Terminal`, attach FitAddon/WebLinksAddon, wire `term.onData` → Rust channel, render incoming bytes via `term.write`, handle resize, disconnect banner, key-pair prompts.

## Backend (Rust)

**DB (`db/mod.rs`)** — additive, same pattern as categories:
```sql
CREATE TABLE IF NOT EXISTS servers (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    host TEXT NOT NULL,
    port INTEGER NOT NULL DEFAULT 22,
    username TEXT NOT NULL,
    key_id TEXT,                 -- nullable: reference to vault key OR NULL for password/pem
    pem_path TEXT,               -- nullable: plain .pem on disk (alternative to key_id)
    auth_method TEXT NOT NULL DEFAULT 'publickey',  -- publickey|password|keyboard-interactive
    saved_password TEXT,         -- nullable, encrypted with vault master password (AES-GCM, same seal() as keys) — only when user opts to save it
    category_id TEXT,            -- nullable, optional group under the category tree
    color TEXT, last_connected_at TEXT, created_at TEXT, updated_at TEXT
);
CREATE TABLE IF NOT EXISTS known_hosts (
    host TEXT PRIMARY KEY, host_key TEXT NOT NULL, fingerprint_sha256 TEXT NOT NULL, first_seen TEXT NOT NULL
);
```
(No foreign keys, matching existing convention.) New methods follow `block()` + `row_to_X` + insert/get/list/update/delete exactly like categories. `server_list` returns each server with `key_name`, `key_type`, `has_key` resolved by joining `keys` by `key_id` so the renderer never needs a second round trip, and flags `key_missing: true` when `key_id` points at a deleted key.

**New IPC commands (`commands/mod.rs`, all `CmdResult<Value>`, registered in `lib.rs`):**
- `server_list` → `{ servers: [{ id, name, host, port, username, authMethod, keyId, keyName, keyType, keyMissing, pemPath, categoryId, lastConnectedAt }] }`
- `server_save(id?, name, host, port, username, authMethod, keyId?, pemPath?, savedPassword?, categoryId?, color?)` → `{ ok, id }`
- `server_delete(id)` → `{ ok }`
- `server_test(id)` → `{ ok, latencyMs }` (async; opens a russh connection with the saved binding, authenticates, closes — validates the whole key+user pairing)
- `server_export_putty(id, outPath)` (optional v2) → save session as a `.reg`-compatible PuTTY profile — explicitly deferred unless you want it
- `terminal_connect(sessionId, cols, rows)` → opens the russh session in a tokio task; returns immediately; all subsequent I/O flows over a **`tauri::ipc::Channel<u8>`-style byte stream** (`terminal_data`, `terminal_resize(cols,rows)`, `terminal_send(bytes)`, `terminal_disconnect(sessionId)` as separate commands against an in-memory `SessionRegistry`; disconnects and closes the session when the vault locks)
- `terminal_list` → `{ active: [{sessionId, serverName, host, port, since}] }`
- `known_hosts_list` → `[{ host, fingerprintSha256, firstSeen }]`
- `known_hosts_forget(host)` → `{ ok }`
- `vault_lock` extended: after clearing the password store, terminate every live session.

All of this keeps private keys in Rust only — the webview never sees key bytes or the master password.

**Dependencies to add (`Cargo.toml`):** `russh` (0.62, default features; pull `ring`-based backend over aws-lc to avoid native build pain on Windows if possible — verify at add time), and re-use the already-present `ssh-key` (host-key type + fingerprint), `aes-gcm`/`chacha20poly1305` + `VaultPasswordStore` (password sealing), `tokio`, `chrono`, `uuid`, `anyhow`. No portable-pty, no libssh2 (its LGPL + static-link constraints make Windows release packaging painful), no Node runtime.

## Renderer

- **Nav**: new sidebar button `Connect` (`data-view="connect"`, `data-nav-ico="monitor-smartphone"`), between Keys and Deploy. Disabled/greyed when vault locked (like Deploy already is).
- **`view-connect` layout**: left column = saved-servers list (name, host:port, username, key/user chip, search box, `New` button); right side = split: top toolbar (server name + status line), middle = the xterm.js terminal div, bottom thin status strip.
- **Server edit modal** (new): Name, Host, Port, Username, **Auth method** segmented (Key / Password / Keyboard-interactive), and a **Key picker** row: dropdown of in-vault keys (name + type + fingerprint), plus `Browse…` for a plain `.pem` file, plus checkbox "save password" (encrypted at rest). When auth = Key, the right-click flow pre-fills this.
- **Terminal session tab management**: only one terminal surface in v1; starting a new connection while one is active asks to disconnect the current one first. (Multi-tab like PuTTY can come later.)
- **Key context menu**: `contextmenu` on a key row opens a small menu with `Use this key to connect…`. Choosing it opens the Connect flow: if the server list is empty → opens the server-edit modal with `key` preselected; otherwise opens a submenu/chooser "new session… or pick a saved server" — selecting a saved server connects immediately with that key+its username overridden by the pairing (per your "user pair"), and "new server…" opens the modal prefilled (key + username editable).
- **Right-click on a *server*** (roadmap item, also include): quick-connect, edit, delete, and "set default key/user".

## Host-key verification (PuTTY-like)

- TOFU: first connection to a host stores its host key fingerprint (`known_hosts` table); subsequent connections compare. Mismatch → hard error with the mismatch message shown in the terminal banner + a button to remove the stale key from `known_hosts` and retry (like PuTTY's "REMOVE AND SAVE" / abort).

## Sync / audit / other views

- No Bitwarden sync of servers in v1 (out of scope; the `SSHSpan` cipher folder semantics stay key-only). Audit log gains `connect.start`, `connect.stop`, `connect.error`, `server.create`, `server.delete` events. Category tree unchanged; servers may optionally carry a `categoryId` but are *not* synced.

## What I will NOT do in v1 (unless you ask)

- PuTTY `.reg` import/export, PuTTY session-tree migration, Pageant agent forwarding, SOCKS/port-forward tunneling, SFTP file browser, tabs-per-session, remote command macros, per-session color/theme profiles, jump hosts. These are natural follow-ups but each is a meaningful chunk; the terminal + key/user binding + right-click flow is the core you asked for.

## Implementation order

1. Add russh to `Cargo.toml`; prove a minimal `terminal_connect` + echo of remote `date` through a test channel compiles and runs (de-risk the trickiest dep before building UI).
2. DB: `servers` + `known_hosts` tables, structs, methods, `server_list` join.
3. `ssh_client/` module: russh connect/auth/pty/resize + `check_server_key` TOFU + in-memory key unseal. `server_test` command.
4. IPC: server CRUD, terminal data/resize/disconnect/send over `ipc::Channel`, registry of live sessions, vault-lock disconnect hook.
5. Vendor xterm.js into `src/renderer/vendor/`; verify it loads under the strict CSP.
6. Renderer: `view-connect` HTML+CSS, server list + edit modal (with key picker), `terminal.js`, key right-click menu → connect flow, nav gating by vault state.
7. Audit events, empty states, resize handling, disconnect banners, host-key mismatch UI.
8. `cargo check` + `npm run build` (both bundles), run the existing test suites, then a live smoke test against a real SSH server if you have one reachable — otherwise a loopback `sshd` test.
